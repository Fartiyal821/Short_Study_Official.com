Database Architecture

SQL & Relational Databases Masterclass

⏱ 14 min read 📖 2,000+ Words ✓ Verified & Current

1. The Relational Model & Database Architecture

Before the invention of relational databases, early software systems persisted data in sequential flat files or hierarchical network databases. In 1970, Dr. Edgar F. Codd published his landmark paper, "A Relational Model of Data for Large Shared Data Banks," proposing that data be organized mathematically into relations (tables) consisting of tuples (rows) and attributes (columns). This mathematical foundation led directly to the creation of Structured Query Language (SQL).

Unlike procedural languages (such as C, Java, or Python) where developers write step-by-step algorithms instructing the computer how to locate and process memory buffers, SQL is a declarative language. In SQL, you describe what data you want to retrieve or mutate, and the database engine's internal Query Planner and Cost-Based Optimizer (CBO) computes the most efficient execution plan using indexes, hash joins, or sequential scans.

Core Relational Building Blocks

  • Tables (Relations): Two-dimensional structured matrices holding records of a specific entity type (e.g., users, orders, products).
  • Rows (Records / Tuples): Individual horizontal entries representing a single entity instance.
  • Columns (Fields / Attributes): Vertical data properties enforced with strict data types (e.g., VARCHAR, INTEGER, DECIMAL, TIMESTAMP, BOOLEAN).
  • Primary Key (PK): A column (or combination of columns) that uniquely identifies each record in a table. Primary keys must be strictly unique and cannot contain NULL values.
  • Foreign Key (FK): A column that references the primary key of another table, establishing a verifiable relationship and enforcing Referential Integrity (preventing orphan records).

2. The Sub-Divisions of SQL Commands

SQL is categorized into five distinct functional command sub-languages:

Category Full Name Core Keywords & Purpose
DDL Data Definition Language CREATE, ALTER, DROP, TRUNCATE, RENAME — Defines and modifies database schema structure.
DML Data Manipulation Language INSERT, UPDATE, DELETE — Modifies data records stored inside tables.
DQL Data Query Language SELECT — Retrieves data from one or more tables without altering stored state.
TCL Transaction Control Language COMMIT, ROLLBACK, SAVEPOINT — Manages transactional boundaries and state persistence.
DCL Data Control Language GRANT, REVOKE — Configures user permissions, role security, and database access controls.

3. DDL: Schema Definition & Table Creation

Let us construct a production-ready e-commerce relational schema demonstrating primary keys, auto-incrementing surrogate identifiers, foreign key constraints, default timestamps, and check constraints:

Code Example 
-- 1. Create the Customers table
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    full_name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    country VARCHAR(50) DEFAULT 'India',
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 2. Create the Products table with check constraint
CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,
    product_name VARCHAR(150) NOT NULL,
    unit_price DECIMAL(10, 2) NOT NULL CHECK (unit_price >= 0.00),
    stock_quantity INTEGER NOT NULL DEFAULT 0 CHECK (stock_quantity >= 0),
    is_active BOOLEAN DEFAULT TRUE
);

-- 3. Create the Orders table with Foreign Key constraint
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INTEGER NOT NULL,
    order_date TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    order_status VARCHAR(30) DEFAULT 'Pending' CHECK (order_status IN ('Pending', 'Shipped', 'Delivered', 'Cancelled')),
    total_amount DECIMAL(10, 2) NOT NULL DEFAULT 0.00,
    CONSTRAINT fk_customer 
        FOREIGN KEY (customer_id) 
        REFERENCES customers(customer_id) 
        ON DELETE CASCADE
);

4. DML: Inserting, Updating, and Deleting Records

Data Manipulation Language commands alter the actual rows inside your tables. Always take precautions when issuing UPDATE and DELETE statements to ensure appropriate WHERE clauses are included.

Code Example 
-- 1. Inserting multiple rows in a single statement
INSERT INTO customers (full_name, email, country) 
VALUES 
    ('Arjun Sharma', 'arjun@example.com', 'India'),
    ('Priya Patel', 'priya@example.com', 'India'),
    ('John Smith', 'john@example.com', 'United States');

-- 2. Inserting products
INSERT INTO products (product_name, unit_price, stock_quantity)
VALUES
    ('Mechanical Keyboard', 4500.00, 25),
    ('Ergonomic Mouse', 2200.00, 40),
    ('USB-C Hub', 1800.00, 0);

-- 3. Updating records with defensive WHERE clause
UPDATE products 
SET unit_price = unit_price * 0.90, stock_quantity = stock_quantity + 15
WHERE product_name = 'Mechanical Keyboard';

-- 4. Deleting records safely
DELETE FROM products 
WHERE stock_quantity = 0 AND is_active = FALSE;

5. DQL: Mastering Data Queries with Filtering & Sorting

The SELECT query is the backbone of relational data retrieval. The logical processing order executed by database engines differs from the syntactic order written by developers:

Code Example 
-- Syntactic Order written by Developer:
SELECT column_name, COUNT(*)
FROM table_name
WHERE condition
GROUP BY column_name
HAVING aggregate_condition
ORDER BY count DESC
LIMIT 10;

-- Logical Execution Order executed by Query Engine:
-- 1. FROM & JOINs (identify source tables and form Cartesian product)
-- 2. WHERE (filter rows at record level)
-- 3. GROUP BY (aggregate records into buckets)
-- 4. HAVING (filter aggregated groups)
-- 5. SELECT (project requested columns and evaluate expressions)
-- 6. DISTINCT (eliminate duplicate projected rows)
-- 7. ORDER BY (sort output rows)
-- 8. LIMIT / OFFSET (slice final result page)

6. Relational Joins Deep-Dive

Relational databases excel because data is normalized across specialized tables to eliminate redundancy. When retrieving consolidated reports, we employ Joins to recombine normalized tables based on shared key relationships.

Join Type Venn Diagram Behavior Common Engineering Use Case
INNER JOIN Returns only records that have matching keys in BOTH tables. Find all orders with a valid, verified customer account.
LEFT (OUTER) JOIN Returns ALL records from the left table, plus matched right records (or NULL if unmatched). Find all registered customers, including those who have never placed an order.
RIGHT (OUTER) JOIN Returns ALL records from the right table, plus matched left records. Rarely needed (equivalent to flipping a LEFT JOIN).
FULL (OUTER) JOIN Returns all records when there is a match in either table (combines LEFT and RIGHT). Data reconciliation audits across legacy and modern systems.
CROSS JOIN Produces the full Cartesian product (N × M combinations). Generating test matrices, t-shirt size × color variations.
Code Example 
-- Comprehensive Multi-Table INNER & LEFT JOIN Query
SELECT 
    c.customer_id,
    c.full_name,
    c.email,
    COUNT(o.order_id) AS total_orders_placed,
    COALESCE(SUM(o.total_amount), 0.00) AS total_revenue_generated
FROM customers c
LEFT JOIN orders o ON c.customer_id = o.customer_id
WHERE c.country = 'India'
GROUP BY c.customer_id, c.full_name, c.email
HAVING COUNT(o.order_id) >= 1
ORDER BY total_revenue_generated DESC;

7. Subqueries, Common Table Expressions (CTEs), and Window Functions

When solving intricate analytical challenges, modern SQL provides Common Table Expressions (CTEs) via the WITH clause, replacing unreadable nested subqueries with clean, modular queries:

Code Example 
-- Analytical Query using CTE and Window Functions
WITH RegionalSales AS (
    SELECT 
        c.country,
        p.product_name,
        SUM(o.total_amount) AS total_sales,
        ROW_NUMBER() OVER (PARTITION BY c.country ORDER BY SUM(o.total_amount) DESC) as sales_rank
    FROM customers c
    JOIN orders o ON c.customer_id = o.customer_id
    JOIN order_items oi ON o.order_id = oi.order_id
    JOIN products p ON oi.product_id = p.product_id
    GROUP BY c.country, p.product_name
)
SELECT country, product_name, total_sales
FROM RegionalSales
WHERE sales_rank <= 3; -- Top 3 highest grossing products per country

8. Transactions & ACID Properties

In mission-critical enterprise systems (such as banking ledgers and healthcare records), operations frequently comprise multiple interdependent SQL statements. An order placement requires deducting account balance, creating an order record, decrementing inventory stock, and recording an audit trail. If the server loses power midway, the database must not be left in a corrupted state. This durability is guaranteed by ACID Properties:

  • Atomicity: "All or nothing." Either every statement within the transaction executes successfully, or the entire transaction is rolled back as if nothing ever occurred.
  • Consistency: The database must transition strictly from one valid state to another valid state, never violating defined constraints (primary keys, foreign keys, check constraints).
  • Isolation: Concurrent transactions executing simultaneously must not interfere with each other. The database enforces isolation levels (Read Uncommitted, Read Committed, Repeatable Read, Serializable).
  • Durability: Once a transaction has been successfully committed (COMMIT), its changes are recorded in non-volatile Write-Ahead Logs (WAL) and will survive subsequent system crashes or hardware failures.
Code Example 
-- Bank Funds Transfer Transaction
BEGIN TRANSACTION;

-- Step 1: Deduct $500 from Account 101
UPDATE accounts 
SET balance = balance - 500.00 
WHERE account_id = 101 AND balance >= 500.00;

-- Step 2: Credit $500 to Account 202
UPDATE accounts 
SET balance = balance + 500.00 
WHERE account_id = 202;

-- Step 3: Verify and permanently commit changes
COMMIT;

9. Common Beginner Pitfalls & Traps

  • The NULL Comparison Trap: In SQL, NULL signifies "unknown value," not zero or an empty string. Therefore, testing WHERE status = NULL will ALWAYS evaluate to Unknown/False! You must explicitly write WHERE status IS NULL or WHERE status IS NOT NULL.
  • Accidental Cartesian Explosion: Executing a join between two tables without specifying the matching key constraint (e.g., omitting the ON clause in SELECT * FROM tableA JOIN tableB;) multiplies all rows together (1,000 rows × 1,000 rows = 1,000,000 rows), crushing server memory.
  • Confusing WHERE and HAVING: The WHERE clause filters individual raw rows BEFORE aggregation occurs; the HAVING clause filters aggregated groups AFTER the GROUP BY stage has materialized.
  • SQL Injection Vulnerabilities: Concatenating untrusted user input directly into SQL strings (e.g., "SELECT * FROM users WHERE email = '" + userInput + "'"). Always use parameterized prepared statements in your application backend!

10. Hands-On Practice Exercises

  1. Calculate Customer Lifetime Value (CLV): Write a query calculating the total spend, average order value (AOV), and total order count for all customers registered in the last 12 months. Include customers who have spent $0 using an outer join.
  2. Detect Duplicate Records: Write a query targeting an un-normalized leads table to locate all email addresses that appear more than once, displaying each duplicate email alongside its frequency count.
  3. Second Highest Salary: Given an employees table with columns id, name, and salary, write an ANSI SQL query to determine the second highest unique salary without using hardcoded limits.

11. Frequently Asked Technical Interview Questions

  1. What is the difference between DELETE, TRUNCATE, and DROP?
    1) DELETE is a DML command that removes rows one by one based on a WHERE clause. It logs every deleted row in transaction logs, activates database triggers, and can be rolled back inside a transaction.
    2) TRUNCATE is a DDL command that deallocates entire data pages containing table rows. It operates orders of magnitude faster than DELETE, cannot filter with a WHERE clause, and does not fire row-level delete triggers.
    3) DROP is a DDL command that completely deletes the entire table structure, indexes, permissions, and data from the database catalog permanently.
  2. How do B-Tree Indexes work, and what are their trade-offs?
    A B-Tree (Balanced Tree) index is an on-disk self-balancing multi-way search tree data structure. It organizes indexed column values in sorted order alongside row pointers (Tuple IDs), reducing table lookup operations from an O(N) sequential full-table scan to O(log N) tree traversals. Trade-offs: While indexes accelerate SELECT queries with equality and range filters, they introduce write overhead on INSERT, UPDATE, and DELETE operations because the B-Tree must be rebalanced upon modifications. Indexes also consume additional disk storage.
  3. Explain Database Normalization: 1NF, 2NF, and 3NF.
    Normalization is the systematic process of designing relational schemas to eliminate redundant duplicate data and prevent insert, update, and deletion anomalies:
    • 1NF (First Normal Form): Each table column must contain atomic (indivisible) values, and each record must be unique.
    • 2NF (Second Normal Form): Must be in 1NF, and all non-key attributes must be fully functionally dependent on the entire primary key (no partial dependencies on composite keys).
    • 3NF (Third Normal Form): Must be in 2NF, and no non-key attribute can depend transitively on another non-key attribute (no transitive dependencies).
