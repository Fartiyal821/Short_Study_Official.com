Python Operators & Conditionals

Arithmetic, Comparison, Logical, Assignment, Membership & Identity Operators, plus if / elif / else — in depth.

Last Reviewed: August 2026 Syllabus: Core Computer Science Level: Beginner → Intermediate

This is Part 2 of a 6-part deep-dive series on Python, continuing from Python Fundamentals. This part covers every operator category Python offers, then shows how they combine inside conditional statements to control program flow. As before, each topic ends with 10 genuinely hard questions.

1. Arithmetic Operators

Python provides seven arithmetic operators: + (addition), - (subtraction), * (multiplication), / (true division, always returns a float), // (floor division, rounds down to the nearest whole number), % (modulus, the remainder after division), and ** (exponentiation). Operator precedence in Python follows standard mathematical rules — exponentiation binds tightest, then multiplication/division/floor-division/modulus (evaluated left to right), then addition/subtraction — and parentheses can always override the default order.

A subtlety many learners miss: floor division and modulus with negative numbers don't behave like they might expect from other languages. Python's % always returns a result with the same sign as the divisor, and // rounds toward negative infinity, not toward zero.

# True division vs floor division print(7 / 2) # 3.5 print(7 // 2) # 3 # Negative numbers behave differently than you might expect print(-7 // 2) # -4, not -3 print(-7 % 2) # 1, not -1
Output3.5 3 -4 1

2. Comparison Operators

Python's comparison operators — ==, !=, >, <, >=, <= — compare two values and always return a bool. A feature unique to Python among mainstream languages is chained comparisons: 1 < x < 10 is valid syntax and evaluates exactly as a mathematician would read it, equivalent to 1 < x and x < 10, without evaluating x twice.

Comparing values of different types is allowed for == and != (Python simply returns False or True rather than erroring), but ordering comparisons like < between fundamentally incompatible types — such as a string and an integer — raise a TypeError in Python 3.

# Chained comparison — evaluates x only once x = 5 print(1 < x < 10) # True # Comparing different types print(5 == "5") # False, no error print(5 < "5") # TypeError!
OutputTrue False TypeError: '<' not supported between instances of 'int' and 'str'
Top 10 Very Hard Questions

  4. What does [1, 2] == [1, 2] return, and why does this differ from how identity comparison would behave on the same two lists?
  5. How does Python compare two tuples, like (1, 2) < (1, 3)? Explain the comparison rule being applied.
  6. What is the result of comparing None == None versus None == 0?

3. Logical Operators

Python has three logical operators: and, or, and not. Unlike many languages, Python's and and or do not necessarily return a bool — they use short-circuit evaluation and return one of their actual operands. and returns the first falsy operand, or the last operand if all are truthy. or returns the first truthy operand, or the last operand if all are falsy. not always returns a proper bool.

This behaviour is frequently used deliberately in idiomatic Python — for example, value = user_input or "default" assigns "default" only if user_input is falsy (empty string, None, 0, etc.), all in one line.

# and/or return an operand, not necessarily True/False print(0 and 5) # 0 (first falsy value) print(3 and 5) # 5 (last value, both truthy) print("" or "hi") # "hi" (first truthy value) print(not 0) # True
Output0 5 hi True

  6. What is the output of not not 5, and what type does it have?
  7. Why does not "False" evaluate to False, even though the string literally contains the word "False"?

4. Assignment Operators

Beyond the basic =, Python offers augmented assignment operators that combine an operation with assignment in one step: +=, -=, *=, /=, //=, %=, **=, along with bitwise variants &=, |=, ^=, >>=, and <<=. For immutable types like int, x += 1 is really shorthand for x = x + 1 — it creates a new object and rebinds the name. For mutable types like list, augmented assignment can (depending on the type) modify the object in place instead.

Python 3.8 introduced the walrus operator :=, which assigns a value to a variable as part of a larger expression — most commonly used to avoid calling the same function twice inside a while loop condition or a list comprehension.

# += behaves differently for list vs tuple lst = [1, 2] lst_id_before = id(lst) lst += [3] print(id(lst) == lst_id_before) # True — modified in place # Walrus operator data = [1, 2, 3, 4, 5] if (n := len(data)) > 3: print(f"List has {n} items")
OutputTrue List has 5 items
Top 10 Very Hard Questions
  1. Why does lst += [3] modify a list in place, while x += 1 on an integer creates an entirely new object?
  2. What is the difference in outcome between lst = lst + [3] and lst += [3] for a mutable list, if another variable also references the same list?
  3. What does the walrus operator := allow you to do that a plain = cannot, inside an if condition?
  4. What is the output of x = 5; x **= 2; print(x)?
  5. Why is x = x = 5 valid but redundant, and what does chained assignment like a = b = 5 actually do under the hood?
  6. What happens if you try to use += on a variable that hasn't been defined yet?
  7. How would augmented assignment behave differently on a tuple, like t = (1, 2); t += (3,), compared to a list?
  8. What is the output of using the walrus operator inside a list comprehension, such as [y := x * 2 for x in range(3)], and what is y equal to afterward?
  9. Why does PEP 8 recommend avoiding walrus assignments in contexts where they hurt readability, despite being syntactically valid almost everywhere?
  10. What is the output of a = 5; b = a; a += 1; print(b), and why doesn't b change?

5. Membership Operators

The in and not in operators test whether a value exists within a sequence or collection — strings, lists, tuples, sets, and dictionaries all support them. For strings, in checks for substring presence, not just individual characters. For dictionaries, in checks against the keys by default, not the values — a common source of confusion for beginners who expect it to search values instead.

Performance matters here: checking membership with in on a list or tuple takes O(n) time (Python checks each element one by one), while checking membership on a set or dict takes O(1) average time, because both are built on hash tables. This is why converting a list to a set is a common optimisation when doing repeated membership checks.

# Substring check print("cat" in "concatenate") # True # Dict 'in' checks keys, not values d = {"name": "Aarav", "age": 16} print("name" in d) # True (it's a key) print("Aarav" in d) # False (it's a value, not a key)
OutputTrue True False
Top 10 Very Hard Questions

6. Identity Operators

is and is not check whether two variables refer to the exact same object in memory — not whether their values are equal. This is fundamentally different from ==, which checks value equality. Two lists with identical contents are == but not is, because they're two distinct objects that happen to hold equal values. The correct, idiomatic way to compare against None is always is None or is not None, never == None.

A famous gotcha: Python caches small integers (typically -5 to 256) and some short strings for performance, so a = 100; b = 100; a is b often returns True — not because of any language guarantee, but because of an implementation detail (CPython's interning). Relying on this behaviour for anything beyond None, True, and False is considered a bug waiting to happen.

# == checks value, is checks identity a = [1, 2, 3] b = [1, 2, 3] print(a == b) # True — same contents print(a is b) # False — different objects # Small-int caching (CPython implementation detail) x = 100 y = 100 print(x is y) # True, but don't rely on this!
OutputTrue False True
Top 10 Very Hard Questions
  1. Why does a == b return True while a is b returns False for the two identical lists in the example?
  2. Why is x is y unreliable for large integers, like x = 1000; y = 1000, compared to small integers like 100?
  3. Why is x == None considered bad practice compared to x is None?
  4. What is the output of "" is "" in most CPython implementations, and why does string interning affect the result?
  5. What does a = []; b = []; a is b return, and why doesn't empty-list caching apply the way small-int caching does?
  6. How would you check whether two variable names refer to the same object, without using is directly?
  7. What is the practical risk of writing if x is 100: instead of if x == 100: in production code?
  8. Why does a is not None read more idiomatically in Python than not a is None, even though both are logically equivalent?
  9. What does type(a) is type(b) check, and how does it differ from isinstance(a, type(b))?
  10. If two variables hold the same tuple of small integers, like a = (1, 2); b = (1, 2), is a is b guaranteed to be True or False? Explain why this is implementation-dependent.

7. The if Statement

The if statement is Python's most basic conditional construct: it evaluates an expression, and if that expression is truthy, the indented block beneath it executes. Python doesn't require a boolean specifically — any expression can be used as a condition, and Python applies its truthiness rules (covered under Data Types) to decide whether to treat it as true or false. There are no parentheses required around the condition and no curly braces around the block — indentation alone defines the block's boundaries, which is why consistent indentation is not just a style preference in Python, it's syntactically required.

age = 20 if age >= 18: print("Eligible to vote") # Any truthy/falsy expression works as a condition name = "" if name: print("Name provided") else: print("Name is empty")
OutputEligible to vote Name is empty

8. if-else, elif & Nested if

if-else provides an alternative block to run when the condition is false. elif (else-if) chains additional conditions to check in sequence, stopping at the first one that's true — Python evaluates an if/elif/.../else chain top to bottom and executes only the first matching branch, skipping the rest entirely, even if a later condition would also have been true. Nested if statements place one if block inside another, useful when a decision genuinely depends on a combination of conditions evaluated in stages — but deeply nested conditionals are usually a sign the logic could be flattened using elif, combined boolean conditions, or early returns inside a function.

marks = 82 if marks >= 90: grade = "A" elif marks >= 75: grade = "B" # matches here, rest is skipped elif marks >= 60: grade = "C" else: grade = "D" print(grade) # Nested if age = 20 has_id = True if age >= 18: if has_id: print("Entry allowed") else: print("ID required") else: print("Too young")
OutputB Entry allowed
Top 10 Very Hard Questions
  1. In the grading example, why does the output stop at "B" even though marks >= 60 is also technically true?
  2. What is the difference in outcome between a chain of independent if statements versus an if/elif chain, when more than one condition is true?
  3. Rewrite a 3-level nested if-statement checking age, membership status, and ID possession as a single flattened condition using and/or. What are the tradeoffs of doing so?
  4. What happens if an elif appears after an else block in the same chain — is this valid Python?
  5. What is the output of an if/elif/else chain where every condition, including the final else, is somehow skipped due to an early return inside a function?
  6. Why is deeply nested if logic (4+ levels) generally considered a code smell, and what refactoring technique commonly fixes it?
  7. What is the difference between if a: if b: ... written as nested statements versus if a and b: ... as a single condition, in terms of behaviour when a is false?
  8. Can an if statement have multiple else blocks? What error occurs if you try?
  9. What is the "dangling else" ambiguity in languages like C, and why does Python's mandatory indentation make this kind of ambiguity structurally impossible?
  10. What is the output of a nested if-else where the inner if's condition depends on a variable modified inside the outer if's own condition check (via a function call with a side effect)?
